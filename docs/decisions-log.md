## Phase 5 — category-first scan, variance-based queue routing, re-weigh on template change
- 2026-09-06: PREMISE CORRECTION — the task described this as building on an existing category/subcategory tree view, pending-item badges, a category management page, and a "queue auto-complete on trust threshold" fix. None of those existed in the repo (verified: single `main` branch, no stashes/worktrees; the trust threshold only flipped `auto_publish` for FUTURE pages and never retroactively resolved already-queued items). Per the user's decision, built the missing prerequisites in this phase, then layered the variance flow on top.
- 2026-09-06: New migration `0005_categories_variance.sql`: a `categories` table (taxonomy tree: 6 groups + the 12 existing leaf slugs, `parent_slug` self-FK, `is_group`, per-category `variance_threshold_pct` NULL=use default, `sort_order`). Leaf slugs deliberately equal the existing flat `attributes.category` / `scrape_templates.category` values so the tree is a DISPLAY layer — no entity data moves. Seed uses `ON CONFLICT DO NOTHING` so admin-edited thresholds survive re-runs.
- 2026-09-06: Same migration adds `review_queue.variance` (NUMERIC %), `variance_detail` (JSONB breakdown), `extraction` (the field-candidate snapshot), `routed_reason` (TEXT), and widens the status CHECK to include `auto_completed`. The `extraction` snapshot is the key design choice: it lets the queue be re-weighed against an updated template WITHOUT re-fetching the page (polite/robots-friendly, and works even if the source is later unreachable).
- 2026-09-06: CATEGORY FIRST — `scanUrl` assigns the category from page signals before any template/processing decision; the category is stamped onto both the queue row and the published entity (`attributes.category`) so it shows in the tree immediately, not only after full processing.
- 2026-09-06: VARIANCE measure (`computeVariance` in template.ts) = % of expected (non-ignore) template fields that deviate, split into missing / unmatched(empty) / structural(present but in a different plain-language `where` than the template learned). Deliberately separate from `templateMatchesPage` (a coarse category-signal gate): variance judges THIS page even for a trusted category. Default threshold `SCRAPER_VARIANCE_THRESHOLD_PCT`=40 (chosen with the user); per-category override on the categories table wins.
- 2026-09-06: HIGH variance OVERRIDES TRUST — in `processCategoryPage`, a page whose variance exceeds the category threshold is routed to the queue (`status queued_high_variance`, row stays `pending`) even when the template has `auto_publish=true`. LOW variance follows the category's current mode (auto-publish if trusted, else manual confirm). Same logic runs in the auto batch + manual apply (shared function), so both paths behave identically.
- 2026-09-06: RE-WEIGH is ONE mechanism (`reweighCategoryQueue`) with TWO triggers, per the spec's "both are really the same underlying mechanism": (a) trust threshold crossed — `pipeline.publishQueueItem` fires an `onTemplateChanged` hook (registered by scan.ts to avoid an import cycle) when `auto_publish` flips false→true; (b) template solved/refined — `refineTemplateAndReweigh` after an admin edits `field_map`. Both recompute each pending item's variance from its stored `extraction` and auto-complete those now within threshold via `autoCompleteQueueItem` (same `upsertEntity` publish path + audit logging as the trust-threshold fix), marking them `auto_completed`. Re-weigh does NOT touch the trust streak (it's a template-level event, not a reviewer confirm), and auto-complete requires the template to be trusted — otherwise low-variance items follow manual-confirm mode exactly as at scan time.
- 2026-09-06: Category management UI = a new admin "Categories" tab: the taxonomy tree with live pending-item badges (leaf `pending_count` + `subtree_pending` rollup for group badges), inline per-category threshold config, and a per-template "solve template" field-map editor that re-weighs on save. Badges/counts come from `GET /admin/categories/tree` and are re-fetched after routing and re-weigh, so they update without a manual refresh.
- 2026-09-06: New endpoints (all documented in api.md): `GET /admin/categories`, `GET /admin/categories/tree`, `POST /admin/categories/:slug/threshold`, `GET /admin/templates/:id`, `POST /admin/templates/:id/refine`, `POST /admin/templates/:id/reweigh`. `/admin/scan` and `/admin/queue` responses extended with variance fields (additive, no breaking change).
- 2026-09-06: VERIFIED with real execution (apps/admin `demo3` + `demo3b`, real dev DB + live starcitizen.tools): scanned PTV (a ground vehicle) — categorized `ship`, 19% variance vs the trusted 43-field ship template; with the ship threshold set to 15% it routed to the queue (`status pending`, `routed_reason high_variance`) DESPITE `auto_publish=true`; "solving" the template (dropping 6 cargo/quarters fields it can't have) dropped variance to 5% and the item AUTO-COMPLETED (`status auto_completed`, entity `ship_ptv` published with regenerated ai_context) and the ship pending badge went 0→1→0. demo3b separately proved the trust-threshold-crossing trigger auto-completes a pre-queued low-variance item via the same mechanism.
